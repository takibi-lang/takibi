# Programs that will not compile

A catalog of kernel defect classes that Takibi rejects at compile time. Each
entry is one defect, shown as one picture, one explanation, and source that a
reader can paste into the compiler to watch it fail.

It exists for three audiences at once. Someone writing kernel code in Takibi,
human or generative, can find out what the language already refuses and why.
Someone preparing a talk can lift a figure and a rejected program without
rereading `test/test_takibi.ml`. And someone deciding whether any of this is
real can run the sample and see the error.

The catalog is indexed by accident, not by language feature. An entry is
titled after what goes wrong on the board -- a blocking call in an interrupt
handler -- rather than after the mechanism that prevents it. `SPEC.md` remains
authoritative for syntax and semantics, and an entry here that starts
explaining the type system instead of the failure has drifted into being a
second specification.

## Conventions

**Numbering.** `NNNN-slug.md`, zero-padded to four digits, assigned in order
and never reused. A number is a permanent handle: it appears in talks and in
commit messages, so a withdrawn entry keeps its number and says so rather than
vanishing and leaving a citation pointing at nothing.

**Status.** `Enforced` when the compiler rejects the program today.
`Partial` when the check covers the common shape and the entry names what
escapes it. `Withdrawn` when the check was removed, with the reason.
`Superseded by NNNN` when a later entry replaces it. A status that is not
`Enforced` is not a failure of the catalog; an entry that claims `Enforced`
while the compiler accepts the program is.

**Test case.** Every entry names the Alcotest case that pins its behavior, by
the exact case name in `test/test_takibi.ml`. This is what makes the catalog
auditable rather than decorative: the sample program and its diagnostic can be
compared against the test that guards them, so a compiler regression turns a
test red instead of quietly turning a documented guarantee into fiction.
Nothing checks that link automatically yet -- see Pending below.

**Figures.** `assets/NNNN-slug.dot` is the source, `assets/NNNN-slug.svg` is
generated by `make -C docs/wont-compile`. Number and slug match the entry so
an orphan on either side is visible.

A figure shows the accident, not the compiler. What goes wrong on the hardware
stays true across compiler changes; a drawing of an inference algorithm goes
stale and nothing catches it. For the same reason figures carry no diagnostic
strings: those belong in the entry text, next to the test case that pins them.

Two mechanical rules keep figures legible for actual readers. The `.dot` sets
`bgcolor`, because a transparent figure with dark text disappears into
GitHub's dark theme. And the Makefile rewrites the emitted `font-family` into a
fallback stack, because Graphviz bakes in text positions computed with its own
metrics and a substituted font overflows the boxes. Avoid `<foreignObject>`:
GitHub sanitizes it and browsers disagree about it.

## Pending

The link between an entry and its test case is a convention today, checked by
nobody. The intended mechanism is a `scripts/check_*` member of `make
langcheck`, which would verify that each named test case exists and that the
sample program and diagnostic in the entry match it. Until that lands, an
entry can go stale the same way any transcribed claim can -- the problem
`scripts/check_documented_counts.py` was written to describe.
